# GUI reliability and wider parity follow-up

17 October 2026. Builds on the [16 October engine integration](engine-integration.md).
The original sibling checkout remains unchanged at `48cf4db`; analysis algorithms
still come from its pinned sources without edits.

## Changes

The project sidebar now uses a native AppKit table with reusable cells, a row
snapshot and guarded selection synchronization. It replaces the SwiftUI List
whose project replacement emitted a reentrant NSTableView delegate warning.
Native delegate callbacks publish selection on the next main-queue turn, guarded
by project identity and final native selection. Programmatic snapshot updates do
not publish back into SwiftUI. Repeated folder reveal no longer publishes an
unchanged expansion set. Search also avoids publishing already-empty results or an already-active loading flag on each keystroke.

Search submission no longer cancels and clears its own results when the text
field commits the unchanged query. Native Return opens the first upstream-ranked
result; filtering to functions then Return opens the structured signature.

Absolute `--dump-file` inputs retain their path spelling, matching the original
CLI. GUI project identity instead consistently uses physical filesystem paths.
Relative labels strip a root prefix only, including the `/tmp`/`/private/tmp`
alias case; they no longer produce malformed labels such as `/privatefile.js`.
The scanner resolves its root once rather than canonicalizing paths per entry.

The rendered audit now sends native mouse/key NSEvents through NSApplication for
file clicks, arrow navigation, rapid navigation, folder collapse/expansion,
disclosure clicks, search typing/submission and selection during project
replacement. It also checks edited, deleted and restored files. These events run
inside the audit app; they do not establish OS HID/accessibility delivery,
production menu shortcuts or input-to-frame latency.

`run_gui_audit.py --run` gates native UI update warnings and writes diagnostics.
`--max-heartbeat-ms 50` enables the optional main-runloop pause budget. Timings
include the next-turn native selection handoff and a presentation observation
interval, while screenshot work remains outside measured intervals.

## Wider engine verification

The upstream corpus manifest, fetcher, corpus scanner and damage probe are now
pinned with the existing validator (255 provenance inputs in total).
`upstream_resilience.py` reuses their discovery, validators, mutation generation
and retention scoring. Every clean and damaged dump is compared in full against
the original CLI on the same path with `QT_HASH_SEED=0`; no fields or arrays are
removed or reordered. Executables and runtime are frozen per run to prevent
concurrent build relinks invalidating signed pages during the sweep.

The full public corpus passes: **6,360 files, all 27 repositories at their pinned
commits, 24 emitted language labels, zero payload differences, zero process
failures and zero original contract issues**. This covers real source files;
it is not a claim that every language's analysis is perfect. Shared-engine
limitations remain shared limitations.

The damage sweep also passes: **8,714 complete clean/mutated dump comparisons,
zero differences and zero failures**. Upstream's reported sample contains 3,313
mutation probes on 880 files across 17 language labels, with 95.8% mean retention
of unaffected symbols. Retention and extra-declaration behavior match the original
because the complete damaged payloads match. This is parity evidence, not a
promise of lossless recovery: upstream still loses symbols on some missing-brace
and unterminated-string cases (notably VB.NET strings in this sample).

The 101 shared fixture cases (625 expectations), 99-file original contract/live
comparison and nine Swift integration tests pass as well.

## GUI results and limits

All 18 functional assertions pass across 45 recorded operations, with no analysis
errors, timeouts, stale final selections or native update warnings. Nineteen
captures cover empty/loading states, minimum size, damaged source, large projects,
native selection/search and a deleted file. Review confirms the disclosure icons,
relative labels and search background are corrected and stale deleted-file symbols
are cleared. The layout still needs the density/navigation work listed below.

| Final Debug operation | Data ready |
| --- | ---: |
| Open original repository | 141 ms |
| Open 500-file JS project | 114 ms |
| Uncached selection, five samples | 79–91 ms |
| Cached data update, five samples | 1.6–1.7 ms |
| Sixteen model selections, final result | 97 ms |
| Native mouse selection | 112 ms |
| Sixteen native Down-arrow events, final result | 58 ms |
| Native five-character search burst, including debounce | 381 ms |
| Native Return to first ranked result | 54 ms |

**The 50 ms main-runloop budget fails.** The final maximum is 84 ms during native
search typing; several cached/presentation and Return operations also exceed the
budget. The preceding expanded runs peaked at 72 ms and 62 ms. Removing redundant
search publications did not establish a consistent latency improvement. These
failures are retained rather than selecting a passing run. A process check found
no leftover engine/audit workers after the final run.

This broadens the 16 October model-only audit with native input work, so the
84 ms maximum is not an equivalent-workload regression comparison with its 59 ms.
Cached data readiness is separate from the later rendering pause. The audit's
10 ms heartbeat and 150 ms presentation observation do not measure OS HID delivery
or input-to-frame latency. Release profiling and isolating repeated SwiftUI view
updates remain necessary before claiming the responsiveness target is met.

The GUI command exits 1 for this performance gate even though functional and
warning checks pass. This is separate from the intentionally failing macOS 14
compatibility gate.

## Release compatibility

The relocated runtime and production app launch pass on this Mac. An explicit
`verify_runtime.py --target-macos 14.0` gate now fails on the six incompatible
transitive libraries, rather than allowing a relocation pass to imply minimum-OS
support. Compatible library builds, clean-machine validation, release notices,
Developer ID signing and notarization remain outstanding.

## Next priorities

1. Build macOS 14-compatible dependencies and pass the explicit compatibility
   gate, then validate on that OS.
2. Extend native coverage to production menus, accessibility/OS input, split
   dragging, wheel scrolling and multiple windows; establish Release p50/p95.
3. Improve filesystem/dependent-result invalidation and active indexed enrichment.
4. Finish type-link navigation, damaged-line markers and inspector/search density.

The [development plan](development-plan.md) gives acceptance criteria. The former
separate-parser plan is retained only as a linked historical archive.

## Reproduce

```sh
swift test --scratch-path /tmp/lumencode-shared-build --disable-sandbox
python3 tools/run_gui_audit.py --build /tmp/lumencode-shared-build --output /tmp/gui-audit --run --max-heartbeat-ms 50
python3 Engine/Upstream/tools/fetch_corpus.py --dest /tmp/lumencode-public-corpus
python3 tools/upstream_resilience.py corpus --cli /tmp/lumencode-shared-build/debug/lumencode-swift-cli --reference-cli /path/to/original/lumencode-cli --root /tmp/lumencode-public-corpus --output /tmp/corpus.json
python3 tools/upstream_resilience.py damage --cli /tmp/lumencode-shared-build/debug/lumencode-swift-cli --reference-cli /path/to/original/lumencode-cli --root /tmp/lumencode-public-corpus --output /tmp/damage.json
python3 tools/verify_runtime.py --runtime .build/EngineRuntime --target-macos 14.0 --output /tmp/runtime-macos14.json
```

The last command currently fails intentionally because packaging is not yet
macOS 14-compatible. GUI runs require a desktop session.
